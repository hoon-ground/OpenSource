내가 제공하는 코드에서 Martin Fowler의 코드 스멜 관점으로 최소 5개 이상의 코드 스멜을 찾아줘.

기준:
- 코드 스멜은 “버그 자체는 아니지만, 더 깊은 설계 문제를 암시하는 구조나 패턴”으로 판단해줘.
- 단순 스타일 지적 말고, 리팩토링 대상이 되는 설계 문제 중심으로 봐줘.
- 아래 범주를 기준으로 분류해줘:
  1. Bloaters
  2. Object-Orientation Abusers
  3. Change Preventers
  4. Dispensables
  5. Couplers

출력 형식:
각 항목마다 아래 형식으로 정리해줘.

1. 코드 스멜 이름
2. 분류(category)
3. 해당 코드 위치(파일명, 함수명, 클래스명, 또는 코드 일부 인용)
4. 왜 이것이 코드 스멜인지
   - 어떤 구조적 문제가 보이는지
   - 왜 유지보수성/확장성/가독성을 해치는지

추가 요구사항:
- 가능한 한 서로 다른 범주의 스멜을 골고루 찾아줘.
- 애매한 경우에는 왜 애매한지도 같이 설명해줘.
- 실제 버그 가능성이 아니라 “설계상 경고 신호”라는 관점에서 설명해줘.

1. Primitive Obsession
분류: Bloaters
해당 코드 위치: app.py, log 딕셔너리 구조 (예: log = {"id": len(logs), "type": log_type, "title": title, "content": content})
왜 이것이 코드 스멜인지:

구조적 문제: 로그 데이터를 단순한 딕셔너리로 표현하고 있어, 관련된 데이터와 동작을 묶지 못하고 있다. 이는 OOP 원칙을 무시하고 기본 타입에 의존하는 패턴이다.
유지보수성/확장성/가독성 해치는 이유: 로그에 새로운 필드나 유효성 검사를 추가할 때마다 모든 관련 코드를 일일이 수정해야 하며, 타입 안전성이 부족해 런타임 오류를 유발할 수 있다. 이는 설계상 경고 신호로, 더 큰 규모에서 데이터 클래스로 리팩토링해야 할 필요성을 암시한다.



2. Data Class
분류: Dispensables
해당 코드 위치: app.py, log 딕셔너리 (예: log = {"id": len(logs), "type": log_type, "title": title, "content": content}) 및 관련 사용 (logs 리스트)
왜 이것이 코드 스멜인지:

구조적 문제: log는 데이터만 담고 있고, 그 데이터를 처리하는 로직이 클래스 외부에 분산되어 있다 (예: write 함수에서 생성, log_detail에서 접근). 이는 클래스가 데이터 운반자 역할만 하는 불필요한 구조이다.
유지보수성/확장성/가독성 해치는 이유: 데이터와 로직이 분리되어 있어, 로그 관련 변경 시 여러 곳을 동시에 수정해야 하며, 코드의 응집력이 떨어져 가독성이 나빠진다. 설계상 경고 신호로, 이 클래스를 진정한 객체로 만들거나 제거하는 리팩토링을 고려해야 한다.



3. Feature Envy
분류: Couplers
해당 코드 위치: app.py, log_detail 함수 (예: log = logs[id])
왜 이것이 코드 스멜인지:

구조적 문제: log_detail 함수가 logs 리스트의 데이터를 직접 조작하고 접근하는 데 집중하고 있어, logs의 내부 구조에 과도하게 의존한다. 이는 함수가 자신의 책임이 아닌 외부 데이터에 "부러워"하는 패턴이다.
유지보수성/확장성/가독성 해치는 이유: logs의 구조가 바뀌면 이 함수뿐만 아니라 모든 접근 지점을 수정해야 하며, 결합도가 높아져 확장성이 떨어진다. 설계상 경고 신호로, 데이터 캡슐화나 별도의 데이터 관리 클래스를 도입해야 할 필요성을 암시한다.



4. Inappropriate Intimacy
분류: Couplers
해당 코드 위치: test_app.py, 테스트 함수들 (예: from app import app, logs 및 logs.clear())
왜 이것이 코드 스멜인지:

구조적 문제: 테스트 코드가 앱의 내부 상태 (logs 글로벌 변수)에 직접 접근하고 수정하고 있어, 앱과 테스트 간에 과도한 친밀함이 생겼다. 이는 모듈 간 경계를 침범하는 패턴이다.
유지보수성/확장성/가독성 해치는 이유: 앱의 내부 구현이 바뀌면 테스트가 깨지기 쉽고, 테스트가 앱의 세부 사항에 묶여 있어 독립성이 떨어진다. 설계상 경고 신호로, 인터페이스를 통한 테스트나 모의 객체 사용을 고려해야 한다.



5. Divergent Change
분류: Change Preventers
해당 코드 위치: app.py, write 함수 (전체 함수)
왜 이것이 코드 스멜인지:

구조적 문제: write 함수가 HTTP 요청 처리, 폼 데이터 검증, 로그 생성, 리다이렉트 등 여러 책임을 동시에 담당하고 있어, 하나의 변경 이유가 여러 측면을 건드린다. 이는 함수가 다중 역할을 하는 패턴이다.
유지보수성/확장성/가독성 해치는 이유: 예를 들어 유효성 검사 로직을 바꾸려면 전체 함수를 수정해야 하며, 확장 시 함수가 더 복잡해져 가독성이 떨어진다. 설계상 경고 신호로, 단일 책임 원칙 위반을 암시하며, 함수 분리나 전략 패턴 적용을 고려해야 한다.



6. Duplicate Code
분류: Dispensables
해당 코드 위치: test_app.py, 각 테스트 함수 시작부 (예: logs.clear() 반복)
왜 이것이 코드 스멜인지:

구조적 문제: 모든 테스트 함수에서 logs.clear()를 반복적으로 호출하고 있어, 동일한 초기화 코드가 중복된다. 이는 코드 재사용을 무시하는 패턴이다.
유지보수성/확장성/가독성 해치는 이유: 초기화 로직이 바뀌면 모든 테스트를 일일이 수정해야 하며, 코드가 장황해져 가독성이 나빠진다. 설계상 경고 신호로, setUp 메서드나 헬퍼 함수로 추출해야 할 필요성을 암시한다. (참고: 이 스멜은 Dispensables 범주에 속하지만, 테스트 코드 특성상 애매할 수 있음 – 실제로는 테스트 프레임워크의 기능을 활용하지 않아 불필요한 중복으로 보임)

이전에 식별한 6개의 코드 스멜 중에서 가장 우선순위가 높은 1개를 선택하고, 그 항목을 실제로 리팩토링해줘.

중요:
- 실제 수정된 코드를 직접 작성해줘.
- 리팩토링의 목적은 외부 동작을 바꾸지 않고 내부 구조를 개선하는 것.
- 기능 추가나 버그 수정이 아니라, 구조 개선에만 집중해줘.
- 수정 범위는 선택한 가장 중요한 코드 스멜 1개를 해결하는 데 필요한 범위까지만 해줘.

작업 절차:
1. 6개 코드 스멜 중 가장 영향이 큰 1개를 선택해줘.
2. 왜 이것이 가장 우선순위가 높은지 간단히 설명해줘.
3. 어떤 SOLID 원칙을 위반하는지 설명해줘.
4. 아래 리팩토링 테크닉 중 어떤 것을 적용할지 선택해줘.
   - Composing Methods: Extract Method, Inline Method
   - Moving Features: Move Method, Move Field, Extract Class
   - Organizing Data: Replace Magic Number, Encapsulate Field
   - Simplifying Conditionals: Decompose Conditional, Replace Conditional with Polymorphism
   - Simplifying API: Rename Method, Hide Delegate
5. 그다음 실제로 코드를 수정해줘.

출력 형식:
1. 선택한 코드 스멜
2. 우선순위가 높은 이유
3. 관련 SOLID 원칙
4. 적용한 리팩토링 기법
5. 리팩토링 전 문제 요약
6. 리팩토링 후 코드 전체
7. 무엇이 어떻게 개선되었는지 설명
8. 추가로 이어서 리팩토링할 수 있는 포인트 1~2개

코드 수정 시 주의사항:
- 기존 동작은 유지해줘.
- 불필요한 대규모 재작성은 하지 마.
- 바뀐 부분이 명확히 드러나도록 해줘.
- 필요한 경우 클래스 분리, 메서드 추출, 조건문 단순화 등을 실제 코드에 반영해줘.
- 가능하면 변수명/함수명도 더 의도가 드러나게 정리해줘.
- 수정된 코드는 바로 복붙해서 사용할 수 있을 정도로 완성된 형태로 작성해줘.
- 설명보다 실제 코드 결과물이 중심이 되게 해줘.

선택한 코드 스멜: Primitive Obsession (Bloaters 범주)

우선순위가 높은 이유: 이 스멜은 log 데이터를 기본 타입(딕셔너리)으로 표현함으로써 전체 앱의 데이터 모델이 약해지고, 다른 스멜(예: Data Class, Feature Envy)의 근본 원인이 된다. 이를 해결하면 타입 안전성과 캡슐화가 향상되어 확장성이 크게 개선되며, 글로벌 상태 문제도 간접적으로 완화된다.

관련 SOLID 원칙: Single Responsibility Principle (SRP) - log이 데이터 운반만 담당해 책임이 분리되지 않음; Open-Closed Principle (OCP) - 새로운 필드 추가 시 기존 코드를 수정해야 함.

적용한 리팩토링 기법: Moving Features - Extract Class (log을 별도의 Log 클래스로 추출하여 데이터와 구조를 캡슐화).

리팩토링 전 문제 요약: log을 딕셔너리로 표현해 타입 안전성이 없고, 데이터와 로직이 분리되어 직접 접근이 용이해 결합도가 높음.

무엇이 어떻게 개선되었는지 설명: Log 클래스를 도입해 데이터 구조를 명시적으로 정의하고, 타입 힌트를 추가해 타입 안전성을 높였다. 딕셔너리 대신 객체를 사용함으로써 데이터 접근이 더 명확해지고, 향후 메서드 추가(예: 유효성 검사)가 용이해졌다. 외부 동작(템플릿 렌더링)은 log.title 등 속성 접근으로 유지되며, 내부 구조만 개선됐다.
